**1．项目背景与任务目标**

我长期研究标准点灯游戏的快速求解算法，当前推进到 **H114**。

游戏规则：

- 棋盘大小为 \(n\times n\)，**n 始终表示棋盘边长**。
- 点击一个按钮，会翻转自身及上下左右相邻的灯。
- 运算在 GF(2) 上进行，翻转对应 XOR。
- 当前 H 系列主要处理**从全部熄灭到全部点亮**。
- 每个按钮只需考虑按或不按。

本会话研究的是**快速求得原算法所规定的一组合法解，并保持规范结果一致**。不能把它直接理解成“求点击次数最少的解”；最少步问题是另一个研究任务。

主要目标按优先级排列：

| 优先级 | 目标 |
| --- | --- |
| 第一 | 保证计算正确，结果与原来较慢的可靠算法一致 |
| 第二 | 严格保持 A/B 两版的数学算法一致 |
| 第三 | 尝试降低任意一般 n 的总体最坏时间复杂度 |
| 第四 | 优化实际运行时间，减少重复计算、内存操作和其他常数 |
| 第五 | 清理确实无用的代码，保持版本完整、说明准确 |

用户希望持续探索能否把一般首行求解核心的复杂度，从 Karatsuba、Toom-Cook、FFT/NTT 对应的上界进一步降低，尤其关注能否减少 \(O(n\log^2n)\) 中的对数因子。

**不能把仅对特殊 n 成立的加速，写成一般最坏复杂度下降。也不能把实测更快写成复杂度降阶。**

**2．现有求解路线与版本背景**

当前算法围绕 Fibonacci 多项式、结构化矩阵和 GF(2) 多项式运算展开，主要包含：

1. 倍增构造所需的 f/c 等多项式及目标向量。
2. 利用对称性等结构缩小问题。
3. 用半 GCD、扩展 GCD 等求 G/U/V。
4. 通过 Laurent 转换、多项式卷积等计算中间结果。
5. 必要时恢复规范解。
6. 运行原有验证。

相关阶段包括构造、GCD、Laurent 核计算、奇异情况恢复及验证。**实际计时标签要按代码中的计时边界解释，不能仅凭标签字母推断它对应哪个函数。**

重要历史路线：

| 版本或阶段 | 主要内容 |
| --- | --- |
| H58 附近 | Fibonacci 倍增构造，降低 f/c 构造成本 |

**3．A/B 一致性的严格要求**

这是用户最重视的要求之一。

| 项目 | 要求 |
| --- | --- |
| A 版 | 多项式系数、查表结果、NTT 余数、扩域算术结果等数据位必须保存为 Boolean |
| B 版 | 主要用 LongWord 打包相同的数据与运算 |
| 数学算法 | A/B 必须使用相同公式、递归、求值插值方法、基转换和求解路线 |
| 分派条件 | 使用相同的逻辑系数长度、阈值及保护条件 |
| 特殊捷径 | 不能 B 有一套加速数学算法，A 却退回另一套一般算法 |
| 结果 | 不仅要都合法，还要与参考算法得到相同的完整规范结果 |
| 性能比较 | 应在相同 n、相同计时口径和编译条件下比较 |

A 中允许整数用于：

- n、维度、次数、长度。
- 循环下标、地址、指针。
- 查表地址及已有的字节索引缓存。
- 常量和计时。

**这些整数不能被用来偷偷保存本应为 Boolean 的算术结果。**

H114 的 A 用 Boolean 数组表示固定宽度的 16/32/64 位数据，模拟 B 对应的整数或扩域运算。B 底层可能使用 Word 表项、QWord 中间乘积；这些属于表示宽度的实现细节，数学运算要与 A 对应。

“A/B 算法一致”不要求源码逐字相同，但不能以表示差异为理由，引入不同的数学路线或不同的系数阈值。

**5．复杂度必须采用的准确口径**

分析时要区分：

- 棋盘边长 n。
- 某次多项式乘法的系数数量 s。
- FFT/NTT 的变换长度 L。
- 首行求解核心。
- 完整棋盘展开、验证、打印或图像输出。
- 固定机器字宽与随 n 增长的理论字宽。

不能把这些量混用。

设 \(M(s)\) 是 s 个二进制系数的多项式乘法成本。半 GCD 的递归可用如下形式分析：

\[
H(s)\le 2H(\lceil s/2\rceil+O(1))+O(M(s)).
\]

对应的一般首行核心上界：

| 后端 | 乘法成本上界 | 一般首行核心上界 |
| --- | --- | --- |
| Karatsuba | \(O(s^{\log_2 3})\) | \(O(n^{\log_2 3})\)，约 \(O(n^{1.585})\) |
| Toom3 | \(O(s^{\log_3 5})\) | \(O(n^{\log_3 5})\)，约 \(O(n^{1.465})\) |
| 精确环 FFT | \(O(s\log s\log\log s)\) | \(O(n\log^2n\log\log n)\) |
| 受支持范围内的整数 NTT | \(O(s\log s)\) | \(O(n\log^2n)\) |
| 当前 Latest 加法 FFT | 可推广的保守上界仍含转换成本 | 保守采用 \(O(n\log^2n\log\log n)\) |

特别注意：

- 当乘法成本是 \(s^\alpha\)、\(\alpha>1\) 时，递归各层几何求和，**不能机械地再乘一个 log**。
- 当前 Latest 的基转换不能直接忽略。
- 当前 `H111Convert` 的一般转换上界仍可能带来额外 \(\log\log\) 因子。
- 固定 GF(2³²)、16 位输入分块和有限长度范围内，可以明确限定模型后采用有界转换因子的工程口径；**这不等于任意扩展 n 的严格渐近证明**。
- H114 的共享和矩阵融合减少了常数，**尚未证明一般最坏复杂度进一步降阶**。
- 特殊尺寸的线性算法不改变所有 n 的一般最坏上界。
- 核心工作空间采用 O(n) 口径；图像、完整棋盘和输出所需资源要另行计算。
- A_out 保留整个棋盘的逐行验证与输出，含 \(\Theta(n^2)\) 工作，不能给整份 out 程序直接标上首行核心的近线性复杂度。

NTT 的具体限制：

| 项目 | 当前实现 |
| --- | --- |
| 模数 | \(p=2013265921=15\cdot2^{27}+1\) |
| 原根 | 31 |
| 最大二次幂变换长度 | \(L\le2^{27}\) |
| 单个二进制卷积系数 | 不超过 L |
| 两个卷积叠加的系数 | 不超过 \(2L\le2^{28}<p\) |

**\(2^{27}\) 是变换/乘积长度约束，不能直接等同于棋盘边长 n 的上限。**

强制 NTT/Latest 比较版在超出支持乘积长度时以 219 退出，避免悄悄换后端；自动版保留精确环 FFT 回退。实际源码还受到容量、内存和索引范围限制。

**9．计时口径及目前测到的结果**

常规 A/B 和各个 100000 比较版：

- 使用原 QueryPerformanceCounter/TimeMark。
- 单位毫秒，保留三位小数。
- 保留原标签，H114 在 GeneMat 后新增 e 收尾。
- 本次总体统计从 MakeMat 内 m 标记之后到 e。
- 包含该区间的构造、求解和验证。
- 不包含 m 之前的准备、启动、原初始化、预热及 e 之后的完整结果导出。
- 按需建立的新算术表，如果发生在计时区间内，则仍计入。
- **它不是整个进程的墙钟时间。**

H114，n=100000，单次测量：

| 算法版本 | A：Boolean，ms | B：LongWord，ms | A/B |
| --- | ---: | ---: | ---: |
| 自动混合 | 368.199 | 16.910 | 21.774 |
| Karatsuba | 375.072 | 14.607 | 25.678 |
| Toom3 | 1372.058 | 201.967 | 6.793 |
| 精确环 FFT | 1983.321 | 81.002 | 24.485 |
| 整数 NTT | 154215.938 | 621.042 | 248.318 |
| Latest 加法 FFT | 3117.057 | 84.246 | 36.999 |

解释这些结果时，应注意：

- A 的自动版与 Karatsuba 差约 1.8%，不能用单次样本确定稳定排名。
- B 的 FFT 与 Latest 差约 4%，也处于接近的速度档。
- 严格 Boolean 的 A_NTT 单次 100000 约需 154 秒；默认连续 101 个 n 可能很慢。
- Latest 表示最新大输入通用路线，**不代表它在 100000 时一定最快**。
- 固定后端比较版的低阈值用于确保执行对应后端，不代表各后端已经调到最佳实际速度。

另有相同最终内核的矩阵对照实验：每个矩阵元素 8192 位，预热一次、串行运行三次，取中位数。

| 矩阵方式 | F/I 数量 | A，ms | B，ms |
| --- | --- | ---: | ---: |
| 8 个独立乘积 | 16/8 | 358.808 | 8.638 |
| 只共享成对乘积 | 12/8 | 274.966 | 6.887 |
| H114 频域融合 | 8/4 | 156.196 | 4.054 |

这组矩阵实验约有 A 2.30 倍、B 2.13 倍收益，**不能直接当成整个点灯求解器的加速倍数**。

**10．对“Karatsuba 为什么最快、NTT 为什么最慢”的已完成分析**

已对测试副本补做调用统计和函数计时，结果仍与完整参考首行一致。补测副本的耗时不同于原表，因此不能把两次测量的数据混在一起计算占比。

主要发现：

| 因素 | 具体情况 |
| --- | --- |
| 实际规模 | n=100000 时关键 GCD 次数上限为 25000 |
| 数据膨胀 | NTT 每个二进制系数变成一个模整数，存储约膨胀 32 倍 |
| Latest 打包 | 16 个输入系数装入一个扩域元素，存储约膨胀 2 倍 |
| NTT 运算 | 奇素数模域中的带进位加减、整数乘法及 Montgomery 约简 |
| A 版代价 | 上述整数运算全部由 Boolean 位模拟 |
| Karatsuba 优势 | 固定叶子、查表、跳零、截断、成对共享、工作区复用较成熟 |
| Toom3 代价 | 求值、精确插值、动态数组和共同输入重复处理 |
| Latest 代价 | 基转换、扩域乘法和变换仍有较大常数 |
| 固定阈值 | 比较版超过 256 个系数即可切入指定后端，明显低于自动版的原阈值 |

NTT 与 Latest 的实际变换统计：

| n=100000 的补测项目 | NTT | Latest |
| --- | ---: | ---: |
| 正逆变换次数合计 | 356 | 356 |
| 变换长度范围 | 4096–32768 | 256–2048 |
| 累计蝶形数量 | 23,265,280 | 1,026,048 |

NTT 蝶形约多 **22.7 倍**。

NTT 的 A/B 调用数量一致：

- Montgomery 函数调用：25,654,350 次。
- 扣除零和单位元捷径后，完整模乘：19,189,275 次。
- 正变换 230 次，逆变换 126 次。
- 矩阵融合触发 14 次。

补测中：

- NTT 正逆变换约占 A 总时间的 90%、B 的 93%。
- `NTTPrepare` 约占 A 的 0.28%、B 的 0.09%。
- 因此主要瓶颈是大量蝶形和模运算，初始化不是主要瓶颈。

A 的 NTT 特别慢，是因为一个模乘内部还要逐位完成整数乘积、32/64 位移位、加减、比较及临时数组处理。GF(2) 的 XOR 不需要进位，成本差别很大。

其他补测发现：

- 两个 GCD 输入在次数上限 25000 的范围内，分别有 2221、2754 个非零系数。
- 固定 Toom3 调用 7180 次；每次有 14 次 `SetLength`，约对应 10 万次动态数组尺寸设置请求。
- 自动混合版只调用 24 次 Toom3。
- 在较少干扰的 B 版 Latest 计时副本中，基转换约占 56%，扩域蝶形约占 34%。

因此，当前后续优化值得重点研究：

1. 在保持 A/B 一致的前提下改进后端切入阈值。
2. 减少 Toom3 的动态数组及重复求值。
3. 降低 Latest 的基转换成本。
4. 继续共享、融合及复用频域结果。
5. 从数学上研究能否真正减少一般最坏复杂度中的对数因子。

**这些是后续方向，尚未形成 H115，也不能把它们写成已完成成果。**
