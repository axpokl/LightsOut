**1．项目背景与总体目标**

这是一个使用 Pascal 实现的标准 n×n 点灯游戏求解器优化项目。计算在 GF(2) 上进行，加法对应异或。

项目已经经历多个版本，当前最新交付为 **H92**。后续通常应从 H92 继续，下一版编号为 H93，除非用户明确要求覆盖当前版本或退回其他基线。

核心目标：

- 寻找适用于一般 n 的快速算法，只求任意一个特解，不求最少点击次数。
- 优先通过数学恒等式、减少运算次数、缩短有效长度、改善递推或分治结构来提速。
- 保持 A/B 两版数学算法一致。
- 在正确性、实际耗时和代码复杂度之间综合衡量，不能只追求漂亮的理论公式。
- 长期希望将当前核心算法整体推进到 O(n log n)，但**目前尚未实现这一目标**。

必须区分以下两个问题：

| 问题范围 | 当前情况 |
|---|---|
| H 系列基准程序 | 主要针对固定全亮目标，求第一行按钮向量，并验证首行方程 |
| 任意显式 n×n 初始盘面的完整求解 | 不能直接宣称当前程序已经实现了完整输入接口 |
| 输出整盘按钮方案 | 输出量本身就是 Θ(n²)，不能把首行核心算法的次二次复杂度套到完整输出上 |

**2．最重要的要求：A/B 数学算法必须一致**

**这是项目的硬性要求，不是尽量满足的偏好。**

| 项目 | 具体要求 |
|---|---|
| A 版表示 | 每个多项式系数、向量元素使用 Boolean |
| B 版表示 | 使用 LongWord 将同一批系数按 32 位打包，并行处理 |
| 两版关系 | B 应是同一数学算法的位打包实现，不能成为另一套求解算法 |
| 数学公式 | 两版计算同一个数学对象，使用相同恒等式 |
| 递推与分治 | 两版递推关系、分治结构和数学分支必须一致 |
| 阈值含义 | 按逻辑系数数量比较阈值，不能混淆 Boolean 元素数和 LongWord 字数 |
| 奇异情况 | 两版采用相同的奇异处理、恢复公式及特解选择方式 |
| 优化同步 | 不能只给 A 换新算法，B 继续旧算法；反过来也不行 |
| 验证方式 | 不能仅凭最终都输出 TRUE 就宣称一致，需要检查相关中间结果及数学步骤 |
| A 的限制 | 不能偷偷将 A 的系数整体打包成整数位运算，从而破坏 Boolean 对照版的意义 |
| B 的要求 | 应保留位并行优势，避免本来可按字处理的操作退化为大量逐位处理 |
| 临时宽类型 | 现有 B 代码使用临时 QWord 拼接两个 LongWord 等操作；这属于位表示处理，不代表可以随意改变算法或整体存储模型 |
| 不能同步的路线 | 应重新设计，或选择共同适用的路线；不能牺牲算法一致性换取单版跑分 |

A/B 耗时比例**不是必须固定达到 20 倍**。但比例明显下降时，需要检查并解释：

1. 是否 A 得到了有效优化。
2. 是否 B 漏掉了可以对应实现的位并行处理。
3. 是否 B 出现退化。
4. 是否两版已经发生数学算法分叉。
5. 是否只是阶段耗时变小、固定开销和计时精度占比增加。

**不能把“比例下降”直接等同于 B 有错误，也不能不检查就归结为正常现象。**

**4．目前的数学结构与阶段含义**

基本算子：

- H：一行上的左右邻接算子。
- J=I+H。
- U=H²+H，也等于 J²+J。
- 运算均在 GF(2) 上进行。

Fibonacci 型多项式约定：

- F₋₁(t)=0。
- F₀(t)=1。
- Fₖ(t)=tFₖ₋₁(t)+Fₖ₋₂(t)。
- Sₙ(t)=F₀(t)+F₁(t)+⋯+Fₙ₋₁(t)。

当前仍沿用多项式分解、扩展 gcd、结构化奇异恢复的主线，没有切换成另一套完整商环求解器。

| 阶段 | 主要工作 |
|---|---|
| f/c | 在 U=t²+t 的分解下构造相关多项式及配套缓存 |
| y | 构造固定全亮目标对应的首行方程右端项 |
| mak | 包含上述构造及相关初始化、缓存处理 |
| q/g | 求 gcd 和 Bézout 系数，使用结构递推、half-gcd 和小块 Euclid 等 |
| z | 将 Bézout 多项式作用到 y，得到中间向量 |
| x | 非奇异时直接恢复；奇异时求解相应结构化方程，得到第一行按钮向量 |
| gen | 验证 Fₙ(J)x=y |
| A_out | 从第一行按钮向量恢复并输出整盘操作方案 |

常用代码变量：

| 变量 | 含义 |
|---|---|
| `gu` | U 变量下的 gcd |
| `qu,qv` | Bézout 系数 |
| `rU` | U 变量下 gcd 的次数 |
| `r0=2*rU` | 相应完整多项式次数，关联秩亏 |
| `y` | 首行方程右端项 |
| `z` | Bézout 作用后的中间向量 |
| `x` | 第一行按钮向量 |

注意：视频文稿、历史说明和源码可能使用不同的 f/c/g/r/d 记号，继续推导前需要核对定义，不能仅凭同名变量直接套用。

**5．当前复杂度结论**

以下针对固定目标的首行核心求解及验证，不包括完整 n×n 输出。

| 阶段 | 当前复杂度 | 说明 |
|---|---|---|
| f/c 构造 | O(n) | Fibonacci 倍增等结构 |
| y 构造 | O(n) | 当前半核构造及展开 |
| q/g | O(n^log₂3)，约 O(n^1.585) | 仍是整体主要瓶颈 |
| z | O(n log n) | H87 后采用快速 Fibonacci 作用，H92 减少其中常数 |
| x，一般情形 | O(n^1.585) | 仍保留通用快速除法路径 |
| x，适用的特殊因子结构 | O(n log n) | H88 的移位/二项式恢复路径 |
| gen | O(n log n) | 快速 Fibonacci 作用 |
| 整体核心算法 | **O(n^1.585)** | **尚未整体达到 O(n log n)** |
| 工作空间 | O(n) | 不包括保存全部历史输出 |
| 完整整盘输出 | 至少 Ω(n²) | 输出量下界 |

必须纠正一个容易混淆的说法：

> 目前不能说“只有 half-gcd 还是 O(n^1.585)，其余全部都是 O(n log n)”，因为一般 x 路径仍有 O(n^1.585) 的上界。

另外，不能简单认为“换成 O(n log n) 乘法，就能自动把 half-gcd 变成 O(n log n)”。一般 half-gcd 的复杂度分析还涉及额外递归层次，必须重新推导。

**7．H92 的具体改动、正确性依据与状态**

H92 以 H91 为基线，主要修改 `ApplyFibonacciFast` 和 B 版对应的 `ApplyFibonacciFastW`。q、mak、x 的核心算法没有改变。

原先求 Sₙ(J)v 时，每个二进制倍增层都同时维护：

- F 对应的两个向量状态。
- S 对应的求和向量状态。

H92 使用恒等式：

**J·Sₙ(J)=Fₙ(J)+Fₙ₋₁(J)+I**

先得到右侧作用结果，再通过一次 O(n) 线性恢复得到 Sₙ(J)v，从而减少每层的求和向量更新。

关键点：

| 项目 | H92 的处理 |
|---|---|
| J 可能不可逆 | 不直接假定 J 存在逆 |
| 解的确定 | 直接计算 Sₙ(J)v 的第一个坐标，用它确定正确解 |
| 首坐标计算 | 利用求和多项式的 Laurent 半核及反射边界公式 |
| 线性恢复 | 使用三对角递推，对应除以 1+t+t² |
| 恢复实现 | 利用 1/(1+t+t²)=(1+t)/(1+t³)，采用共同的 32 系数前缀步骤 |
| A/B 同步 | A 使用 Boolean，B 使用 LongWord 表示同一运算 |
| 适用范围 | 新恢复路径用于 `summed=true` 且 `degree<=hi+1`；超出该范围保留原求和递推 |
| A 的额外改善 | 按内部区域和反射边界拆分循环，减少逐系数边界判断 |
| B 对应情况 | B 在 H89 已有内部区域按字读取处理，H92 没有为 gen 更换另一套数学公式 |

H92 已完成的验证：

| 验证项目 | 结果 |
|---|---|
| 独立 Fibonacci 与求和算子检查 | 每版 2494 组通过 |

| 大尺寸算子检查 | 最大 n=100000 |

**9．计时规则与后续验证流程**

原始日志的数值与字母标签位置容易读错，必须沿用项目规则：

| 阶段 | 提取规则 |
|---|---|
| mak | 每次运行只取第一行 m 后、c 前的值 |
| q | 每行 q 后、z 前的值，取中位数 |
| z | 每行 z 后、d 前的值，取中位数 |
| x | 只统计存在 x 标签的行，取 x 后、gTRUE 前的值，再取中位数 |
| gen | 取后一行开头、m 前的值；第一行开头不是上一轮 gen，必须排除 |

现行正式比较流程：

1. 同一环境、相同编译条件，比较旧版和候选版。
2. 标准区间 n=9900–10000，共 101 个尺寸。
3. 旧版、新版交替运行，避免固定顺序造成偏差。
4. 每版运行 12 轮。
5. 每轮按上表提取阶段值，再对 12 轮取中位数。
6. 保留原始日志，遇到 FALSE 立即判定验证失败。
7. 分别观察五个阶段，不能仅给总时间。
8. 修改数学核心时，增加针对该变化的独立检查。
9. 覆盖字边界、递归阈值附近、奇异尺寸、较大尺寸和输入输出别名等实际相关风险。
10. 测试通过后，交付正式三文件 ZIP；测试脚本和日志可作为内部工作文件，不必全部塞入交付包。

诊断测试可以启用范围检查等手段，但正式性能比较不能因此改变两版的编译条件。

**12．下一步优化方向**

下一版应先结合用户对 H92 的实测反馈重新评估热点。

| 优先级 | 方向 | 判断依据 |
|---|---|---|
| 高 | q/g 的结构性优化 | 仍占核心耗时的大部分，最有机会改善整体速度 |
| 高 | 减少 half-gcd 中重复矩阵作用、乘法或可证明无用的系数计算 | 应先定位实际热点，不能只凭理论猜测 |
| 中 | z 中半核构造、Fibonacci 状态或恢复过程的重复计算 | H92 已减少求和状态更新，仍可进一步分析 |
| 中 | 检查 B 是否遗漏对应的位并行实现 | 以实际操作和瓶颈为依据，不以固定倍数为目标 |
| 较低 | mak 的常数优化 | 当前成本较小，且首次构造与逐规模耗时统计不同 |
| 较低 | 一般 x 路径 | 平均占比较小，但仍关系到最坏复杂度及特殊慢例 |

**继续工作的原则：先核实 H92 源码和用户反馈，明确下一版影响的阶段与数学依据，再同步实现 A/B，完成独立正确性检查和阶段计时，最后交付三文件 ZIP、优化说明及版本表格行。**
